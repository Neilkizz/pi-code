## 2. 性能指标

### 2.1 激活性能

| 指标 | P95 目标 | 说明 |
|---|---|---|
| **冷激活** | ≤ 800 ms | 扩展遵循延迟激活原则，`activationEvents` 仅为 `onStartupFinished` 和 `onCommand:pi.showChat`，首次使用前不启动模型连接、不扫描仓库、不创建后台进程 |

**设计依据**：

- Extension Host 激活只注册命令、视图和设置监听器，不执行任何 I/O 密集型操作
- 无 `*` 通配符激活事件
- React Webview 资源在首次打开聊天面板时才加载

### 2.2 会话性能

| 指标 | P95 目标 | 说明 |
| --- | --- | --- |
| **打开会话界面** | ≤ 1.5 s | Webview 从磁盘加载已构建的 React bundle（188 KiB），初始化聊天 UI |
| **新建会话** | ≤ 500 ms | 仅创建进程间通信管道，不启动模型连接 |
| **会话恢复** | ≤ 1 s | 100 个历史会话下列表加载时间 |
| **删除会话** | ≤ 200 ms | 清理临时文件和检查点 |

**设计依据**：

- Webview bundle 188 KiB（production, minified），单次加载
- 会话元数据以 JSON 文件存储，无需数据库查询
- 模型连接在新会话首次发送消息时才建立

### 2.3 搜索性能

| 指标 | P95 目标 | 说明 |
| --- | --- | --- |
| **普通仓库搜索** | ≤ 500 ms | 搜索结果依赖 pi CLI 的搜索能力，扩展本身仅转发请求并渲染结果 |
| **10 万文件仓库搜索** | ≤ 2 s | 大规模仓库下首次搜索耗时 |

**设计依据**：

- 搜索操作完全委托给 `pi` CLI，扩展层仅负责 IPC 通信和结果渲染
- 搜索结果受文件系统缓存影响
- 大仓库支持依赖 `pi` CLI 的渐进式搜索策略

### 2.4 编辑与 Diff 性能

| 指标 | P95 目标 | 说明 |
| --- | --- | --- |
| **打开 Diff 视图** | ≤ 500 ms | VS Code 原生 Diff 编辑器 |
| **自动打开并定位修改文件** | ≤ 300 ms | Agent 开始修改文件时，VS Code 自动打开目标文件并滚动到修改位置 |
| **接受/拒绝 Diff 块** | ≤ 100 ms | 通过 VS Code TextEdit API 应用修改 |

### 2.5 中断性能

| 指标 | P95 目标 | 说明 |
| --- | --- | --- |
| **点击停止到任务停止** | ≤ 1 s | 终止 pi CLI 子进程，清理挂起的工具调用 |
| **终端命令停止** | ≤ 3 s | 终止命令及其子进程 |

### 2.6 内存使用

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| **空闲态内存** | ≤ 150 MB | VS Code Extension Host 在扩展处于 idle 状态时的增量内存 |
| **单会话运行** | ≤ 400 MB | 包含 Webview 渲染、消息历史、模型响应缓存 |
| **多会话运行（4 个）** | ≤ 700 MB | 4 个并行会话的总内存占用 |
| **内存泄漏** | 无持续线性增长 | 8 小时持续使用后内存应保持稳定 |

**设计依据**：

- 会话消息以文件形式持久化，内存中仅保留当前可见消息
- Webview 通过 `acquireVsCodeApi()` 与 Extension Host 通信，不保留整块 DOM 状态
- 工具调用结果按需加载，不在内存中累积全部历史

### 2.7 构建产物大小

| 产物 | 大小 |
| --- | --- |
| Extension Bundle (`dist/extension.js`) | ~39 KiB |
| Webview Bundle (`webview/out/*`) | ~188 KiB |
| VSIX 安装包 | ~250-350 KiB |

## 3. 并行会话隔离

| 指标 | 标准 |
| --- | --- |
| 最大并行会话 | 4 个 |
| 消息串扰 | 零容忍 — 每个会话拥有独立的 `pi` CLI 子进程、独立的 RPC 连接和独立的消息队列 |
| 工具执行隔离 | 各会话的文件操作和命令执行完全隔离 |
| 流式互不干扰 | 4 个并发测试中无跨会话流式内容串扰 |

**设计依据**：

- 每个会话对应一个独立的 `pi` CLI 子进程
- RPC 通信通过独立管道（stdin/stdout）进行
- Extension Host 层按会话 ID 路由所有消息
- 默认 `pi.maxConcurrentSessions` 配置为 3（可调至 10）

## 4. 稳定性测试

| 指标 | 标准 |
| --- | --- |
| **连续运行** | 8 小时无 Extension Host 崩溃 |
| **Provider 断连恢复** | 无需重载扩展即可创建新会话 |
| **大输出处理** | 10 MB 命令输出不导致 Webview 假死（使用截断/分页策略） |
| **Webview 长文本滚动** | 无明显卡顿或整页冻结 |
| **进程崩溃恢复** | `pi.autoReconnect` 启用时自动重启子进程 |

## 5. 性能风险评估

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| pi CLI 启动延迟 | 首次消息延迟增加 | 设置超时阈值，失败时有重试机制 |
| 大规模仓库文件枚举 | VS Code UI 冻结 | 渐进式读取、.gitignore 过滤、二进制文件跳过 |
| 模型响应过慢 | 用户体验下降 | 流式渲染让用户看到实时进度，不阻塞 UI |
| 同时多会话资源争抢 | CPU/内存压力 | `maxConcurrentSessions` 硬限制，默认 3 |
| 大消息历史 | Webview 渲染变慢 | 消息虚拟滚动、历史按需加载 |

## 6. 优化建议

| 优先级 | 建议 | 预期收益 |
| --- | --- | --- |
| P0 | 确保延迟激活实现正确 | 冷激活 P95 ≤ 800 ms |
| P1 | Webview bundle 使用代码分割 | 减少首次加载时间 |
| P1 | 实现消息虚拟滚动 | 提升长对话渲染性能 |
| P2 | 会话消息分页加载 | 降低单会话内存峰值 |
| P2 | 添加内存泄漏检测 CI 步骤 | 防止回归 |
| P3 | 大输出流式写入临时文件 | 避免 Webview 处理 10MB+ 字符串 |
